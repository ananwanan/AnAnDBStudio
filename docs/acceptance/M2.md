# M2 — SQL IDE and execution

Date: 2026-11-11. Base: `dev` at `2f9094f` (M2.1 PR #8 merged).
Implementation branch: `feat/m2-sql-execution`.
Status: implementation complete; automated evidence below; desktop milestone sign-off pending.

## Delivered behavior

- One owning thread per connection. The global registry lock is released before database work; another connection and the connection list stay responsive. A busy connection rejects another query/schema request instead of queuing unbounded work.
- `start_sqlite_query`, `poll_sqlite_query`, `cancel_sqlite_query` are the only new commands. Capabilities and command manifest are updated. SQL semantics stay in the SQLite driver; Tauri only adapts the manager.
- SQLite's own `Batch` parser handles strings, comments, quoted identifiers and trigger bodies. Statements execute in order and stop at the first error. Results preserve column position, NULL, int64 decimal strings, real strings (including non-finite values), TEXT, hex BLOB, and invalid UTF-8 TEXT bytes.
- SQL errors include statement index and a UTF-16 source offset; syntax errors use SQLite's token offset when available. Other errors point at the start of the failing statement. Monaco marks the original selection/script location only while the draft still matches the executed text.
- Ctrl/Cmd+Enter and Execute run the selection, or the entire script without a selection. Binding to a live connection is required. Every execution on a read-write connection requires confirmation, including through the shortcut.
- Results show elapsed time, status, statement selection, direct affected-row count (excluding trigger side effects), transaction status and preview truncation. Results are read-only. Data is rendered as text, never HTML.
- Session-only history retains the latest 50 completed jobs, including failed/cancelled jobs; restoring creates an unbound draft and never runs SQL. No history or database results are written to logs/localStorage. Existing draft persistence remains unchanged.

## Execution semantics and limits

- No implicit encompassing transaction. SQL writes outside explicit BEGIN/COMMIT follow SQLite autocommit. On an error/cancellation/timeout, a still-open transaction is rolled back; earlier committed statements remain committed. UI must never imply cancellation undoes committed writes.
- A successful script may leave an explicit transaction open for a later COMMIT/ROLLBACK on the same connection. Closing the connection interrupts active work, finalizes statements and rolls back uncommitted work.
- Cancellation uses a job-specific flag checked before statements, between rows and every ~1000 VM instructions. Timeouts are 1–300000 ms at the backend (UI: 5 s, 30 s, 5 min). Lock waits are capped at 100 ms; cancellation is cooperative, not a hard real-time deadline. SQL cannot change that busy timeout.
- At most 32 connections, one active operation and one retained result per connection. A new job replaces that connection's prior result. Frontend retains up to 8 completed previews plus active jobs; close/reopen tabs does not lose active job ownership.
- SQL input <=256 KiB, <=100 executable statements, <=128 columns, <=200 preview rows per statement, <=16 KiB per TEXT/BLOB cell and a conservative 1 MiB aggregate preview payload budget. Oversized cells produce an explicit error. No silently truncated cell content. Result limits are enforced during stepping, not after full materialization. For DML RETURNING, rows beyond preview limits are drained to finish the statement; affected rows still report the full direct write count.
- Requests are demand-polled at 150 ms, one response at a time. There is no event backlog or unbounded producer. M3 will replace the fixed preview with paging/streaming and a virtualized grid; no AG Grid dependency is added for this bounded M2 preview.
- ATTACH, DETACH and VACUUM INTO are blocked by the SQLite authorizer: arbitrary SQL cannot create/open secondary file paths. Extension loading is not enabled. Sensitive schema/connection failures retain existing generic error codes/messages.
- Unbound SQL parameters are explicitly rejected. Use SQL literals in the editor; typed application operations should still bind values.
- Schema Explorer is refreshed explicitly after DDL. SQL completion/EXPLAIN can be entered using SQLite SQL; richer context completion and dedicated plan visualizations are not part of this closeout.

## Dependency change

`fallible-iterator` 0.3.0 (already transitive through rusqlite) becomes a direct dependency for SQLite's `Batch` iterator. Its package declares MIT/Apache-2.0; both permit the intended distribution with applicable notices. Existing rusqlite enables its `hooks` feature for cancellation/authorizer callbacks. No new frontend dependency; product license remains undecided.
